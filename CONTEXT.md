# ProfConnect — context for a new chat

Paste this into a new conversation to bring an assistant up to speed on this project without re-deriving everything from scratch. It complements `README.md` (which documents the app for a developer); this file is aimed at an AI assistant picking up where a previous session left off.

## What this project is

ProfConnect connects students and professors at Thapar Institute. React/Vite frontend, FastAPI backend, Supabase (Postgres) database, Socket.IO for anything real-time. Full architecture, data model, and API reference live in `README.md` at the project root — read that first for the "what exists and how it fits together" picture. This file is about *how the project got here* and *things worth knowing before touching it again*.

## Environment quirks specific to this project

- **The project folder often can't be mounted into a bash/shell sandbox.** Use `Read`/`Write`/`Edit`/`Glob`/`Grep` directly on the host path (`/Users/yashrajsharma.exe/Desktop/PROF-CONNECT-main`) for all real edits. Only use a shell for throwaway verification work (see next point), copying files into a scratch/outputs directory first.
- **In a Cowork/remote-devices session (no direct host-path Read/Write), the same "can't mount" issue shows up as `device_bash`'s `$HOME/mnt/<folder>` mount failing outright** — `device_list_dir`/`device_stage_files`/`device_commit_files` still work by the file's real host path, though. The pattern that works: `device_stage_files` the specific files you need into the container's `/mnt/user-data/uploads/...`, edit local copies under `/tmp` (files under `/mnt/user-data/uploads/` are read-only), run the same offline verification described below against those copies, then `device_commit_files` (with `stagedPath` under `/mnt/user-data/outputs/` and the real device path + `expectedMtimeMs` from the stage call) to write them back.
- **Verification pattern used throughout this project:** since the real venv/node_modules aren't reachable from a sandbox shell, syntax/logic checks were done by reconstructing minimal stub versions of dependencies in a scratch folder — e.g. a fake `app/db.py` with `supabase = None`, a fake Supabase client class supporting `.table().select().eq().insert().update().execute().data`, then running real `python3 -c "..."` import + behavior tests against the *actual* router file content (copied in verbatim). Same idea on the frontend: stub out sibling imports, then run real `esbuild` against the actual file content to catch syntax errors. This is slower than just editing and hoping, but it caught several real bugs (see "Bugs found and fixed" below) before the user ever ran the app. Worth continuing this habit for non-trivial backend/frontend changes.
- **User runs the backend manually** (`cd server && source .venv/bin/activate && python run.py`) and the frontend separately (`npm run dev`). Changes to backend code require the user to restart the backend process — `--reload` is on, but new *router registrations* in `main.py` and new *module-level imports* sometimes still warrant a manual restart mention, since the user has been caught by this before.
- **The user's Python venv has hit `[SSL: UNEXPECTED_EOF_WHILE_READING]` connecting to Supabase**, caused by a Python 3.14 + older `httpx`/`httpcore` incompatibility with OpenSSL 3.x's stricter `close_notify` requirement. Fixed once by `pip install --upgrade supabase httpx httpcore`. If DB-backed endpoints all start returning 503 again with that SSL error in the log, that's the first thing to check — it's an environment issue, not an app bug.

## Conventions established in this codebase (follow these in new work)

- **JWT claims, not request bodies, are the source of truth for identity.** Every protected endpoint calls `require_claims(authorization)` (from `auth_utils.py`) and derives `student_id`/`teacher_id` from `claims["sub"]` + `claims["role"]`, then checks ownership against whatever record is being read/written. Never trust an ID passed in the request body for authorization decisions.
- **Notification creation is always best-effort and swallows its own exceptions.** A notification failing to write must never break the booking/response/message action it's attached to. Wrap it in its own `try/except: pass` at the call site, on top of `notify()`'s own internal exception handling.
- **New Supabase-backed routers get a `_run_query`-style wrapper** that catches any exception and re-raises as a clean `HTTPException` (with a specific, actionable message when the failure looks like a missing table), rather than letting a raw exception escape and produce a browser-level "Load failed."
- **Mapper functions live in `src/lib/profile.js`**, one per view-shape (`mapStudentProfile`, `mapTeacherCard`, `mapTeacherProfile`) — DB rows are never rendered directly, always passed through a mapper first.
- **Real-time features reuse the existing single Socket.IO server** (`server/app/sockets.py`) rather than spinning up new infrastructure — a broadcast room for "everyone should see this" (availability), a per-user room pattern (`notify:{role}:{id}`) for "only this one person should see this" (notifications).
